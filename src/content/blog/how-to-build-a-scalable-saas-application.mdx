## 1. Multi-Tenancy: Choosing Your Data Isolation Strategy

When engineering a SaaS application, tenant isolation is your most critical structural decision. There are three primary multi-tenant database patterns:

### A. Shared Database, Shared Schema (Row-Level Isolation)
- **Mechanism:** Every table includes an indexed `tenant_id` column.
- **Pros:** Lowest operational overhead, cost-effective resource pooling, simplified migrations.
- **Cons:** Accidental data leakage risks if queries fail to enforce tenant constraints.
- **Recommended Implementation:** Use PostgreSQL Row-Level Security (RLS) or Prisma Client extensions that inject `tenant_id` filters into every database query automatically.

### B. Shared Database, Separate Schema
- **Mechanism:** One database instance where each tenant is allocated their own schema namespace (`tenant_acme.users`, `tenant_beta.users`).
- **Pros:** Logical boundary separation, per-tenant database backups.
- **Cons:** Migration complexity multiplies linearly with tenant count.

### C. Database-per-Tenant (Isolated Hardware)
- **Mechanism:** A distinct PostgreSQL instance or database cluster per customer.
- **Pros:** Maximum compliance, absolute hardware isolation.
- **Cons:** Astronomical infrastructure bills for early-stage startups.

For 95% of venture-backed and bootstrapped SaaS startups, **Shared Database with PostgreSQL Row-Level Security (RLS)** offers the ideal blend of enterprise-grade security and economic efficiency.

## 2. Authentication & Role-Based Access Control (RBAC)

Never build custom password hashing algorithms from scratch. Rely on battle-tested protocols (Argon2id, OAuth 2.1, OIDC) and separate authentication from authorization:

1. **Identity Layer:** Verify *who* the user is via secure session cookies (`HttpOnly`, `SameSite=Lax`, `Secure`).
2. **Organization / Tenant Context:** Determine *which organization* the user is actively operating within.
3. **Permission Matrix:** Enforce hierarchical roles:
   - `Owner`: Billing, organization deletion, API credentials.
   - `Admin`: User invites, team roles, system settings.
   - `Member`: Core application workflow read/write.
   - `Viewer`: Read-only access with export restrictions.

## 3. Subscription Billing & Webhook Idempotency

Integrating payment platforms like Stripe or LemonSqueezy seems straightforward until race conditions appear.

### The Golden Rule of Webhooks: Idempotency
Network requests fail, and billing providers frequently retry events. Your webhook listener must be strictly idempotent:

```typescript
// Example: Processing Stripe webhook events safely
async function handleStripeWebhook(event: Stripe.Event, db: Database) {
  // 1. Verify webhook signature cryptographically
  // 2. Check if event ID was previously processed
  const existingEvent = await db.processedEvents.findUnique({
    where: { id: event.id }
  });

  if (existingEvent) {
    return { status: 'already_processed' };
  }

  // 3. Process inside a database transaction
  await db.$transaction(async (tx) => {
    switch (event.type) {
      case 'customer.subscription.updated':
        await syncSubscriptionStatus(tx, event.data.object);
        break;
      case 'invoice.payment_failed':
        await notifyCustomerBillingFailure(tx, event.data.object);
        break;
    }

    // 4. Record event as successfully handled
    await tx.processedEvents.create({
      data: { id: event.id, processedAt: new Date() }
    });
  });
}
```

## 4. Asynchronous Workflows and Background Queues

Never block your user-facing HTTP request-response cycle on long-running tasks. Tasks such as PDF generation, third-party CRM syncing, data exports, and transactional email dispatch should immediately be handed off to a persistent background queue (e.g., BullMQ with Redis or Cloudflare Queues).

The client should receive a `202 Accepted` response with a status polling URL or a WebSocket channel notification upon completion.

---

## 5. Observability and Error Tracking

Before launching, wire up structured JSON logging and distributed tracing:
- Request correlation IDs (`x-request-id`) injected at the API gateway and passed through all database queries.
- Error alerting with contextual breadcrumbs (user ID, tenant ID, request parameters).
- Metric instrumentation for P95 and P99 response latencies.
